# Protecting a local Invora shop against Docker or disk loss

The live database and uploads are already stored on the computer's hard drive, in Docker Desktop's named volumes `invora_database` and `invora_documents`. A container crash or removal does not remove a named volume. A Docker factory reset, volume removal, Docker Desktop uninstall, failed drive or stolen computer can remove both. Docker's [volume guide](https://docs.docker.com/engine/storage/volumes/) and [Desktop recovery guide](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/) explain this distinction. Do not use `docker compose down -v` for ordinary restarts.

For a shop, use three independent copies: the live volumes; encrypted, dated snapshots on a separate physical drive; and an encrypted copy in a private cloud bucket. A second folder on the same internal drive only protects against some accidental deletions, not drive failure. The cloud bucket stores recovery archives; it is not a second live PostgreSQL database and does not synchronize two installations.

## Available backup command

`scripts/backup-offsite.sh` wraps the existing signed and encrypted `scripts/backup.sh`. It pauses the API and web services, captures a consistent PostgreSQL dump and uploaded documents, then restarts only services that were running. It retains the archive in a normal host folder outside Docker, writes a SHA-256 sidecar, and copies it to an existing second-drive folder and/or an [rclone](https://rclone.org/) remote. A failed copy exits with an error; it does not delete earlier backups or the database. It does not silently create a missing drive folder, and rejects a configured second-drive folder on the same filesystem as the local archive. Confirm that the second filesystem is actually on a different physical drive; a separate partition of the same drive is insufficient.

Configure the recipient public key and separate signing private key as in [deployment](deployment.md#backups). Keep the recipient **private** key and trusted signing **public** key offline, separate from the shop computer. Do not put them or the shop's `.env` into a public repository or share them in support messages. The backup is encrypted before upload, but the live database and ordinary uploads still rely on host disk encryption and operating-system access control.

Example from the Invora installation directory, after mounting a genuine external drive and configuring an rclone remote called `shopbackup`:

```sh
export BACKUP_PUBLIC_KEY=/private/path/recipient-public.pem
export BACKUP_SIGNING_KEY=/private/path/signing-private.pem
export BACKUP_DESTINATION=/private/path/invora-backups
export BACKUP_EXTERNAL_DIR=/Volumes/ShopBackup/Invora
export BACKUP_RCLONE_REMOTE=shopbackup:private-invora-bucket/shop-01
bash scripts/backup-offsite.sh
```

Use either `BACKUP_EXTERNAL_DIR` or `BACKUP_RCLONE_REMOTE`, preferably both. Prepare the drive folder and private bucket before the first run. The script does not create cloud accounts or keys, choose retention, install a scheduler, or send alerts on its own. Schedule it after closing each business day; if Docker is stopped, that run fails and must be retried. A macOS LaunchAgent can catch up after sleep, but a powered-off, broken or inaccessible Mac cannot upload. Keep several dated generations and check the last successful backup every morning. Never rely on a single latest file; do not use `rclone sync`, because it can remove older remote copies. A backup every 24 hours can lose up to 24 hours of new transactions after a complete primary-disk failure. Choose a shorter interval if that is unacceptable and make sure the brief billing pause is acceptable.

Back up the matching private `.env` **separately in protected recovery storage**. It contains connection and signing secrets and is needed when moving the shop. This script intentionally uploads only its encrypted database-and-documents archive, not `.env`. Keep a written record of which `.env` and decryption key belong to the shop, and verify access to both without exposing them to staff. Retain the original computer until the new one has been restored and checked.

## Free cloud space

As of October 2026, [Backblaze B2](https://www.backblaze.com/cloud-storage/pricing) advertises the first 10 GB of stored data free. [Cloudflare R2 Standard](https://developers.cloudflare.com/r2/pricing/) includes 10 GB-month per month and operation allowances; its free allowance does not apply to Infrequent Access. These are storage allowances, not guarantees that all future backups or operations will remain free. Check the current price and usage dashboard before activating a bucket. Use a private bucket and a scoped application key. Cloud account credentials belong to the shop owner; do not paste them into chat or package them with the application. Prefer a bucket retention/lock rule or a separate account policy that prevents a stolen shop-computer key from deleting old backups. A simple upload key is not a substitute for tested recovery.

For a private Backblaze bucket, create a **new application key restricted to that bucket**, not a master key. In the standard [B2 web console](https://www.backblaze.com/docs/cloud-storage-create-and-manage-app-keys), open **B2 Cloud Storage → Application Keys → Add a New Application Key**. If the account instead uses the [Enterprise console](https://www.backblaze.com/docs/cloud-storage-create-and-manage-application-keys), open **Access Control → Application Keys → Create App Key**. Choose the backup bucket, allow Read and Write, and select “Allow List All Bucket Names” if the console offers it. Leave a file-name prefix blank for initial setup. Save the resulting key ID and application key privately when shown; the application key is only displayed once. [Rclone's B2 guide](https://rclone.org/b2/) documents the account/key mapping. Never type either secret in a chat message or a repository file. A bucket ID alone cannot authenticate an upload.

For a shorter setup, run `python3 scripts/configure-backblaze.py --bucket your-bucket-name` from the installation folder in your own Mac Terminal. It asks for the keyID and applicationKey locally, hides the applicationKey while typing, checks the pair with Backblaze's authorization API, then tests bucket access. It saves the remote only if both checks pass. Enter the **keyID**, not the bucket ID, account ID, or key name. Use the applicationKey displayed once when that **same** keyID was created. If the applicationKey was not saved, create a new scoped key; Backblaze will not show the old secret again. The helper never passes the applicationKey as a command-line argument. The B2 backend requires the actual applicationKey in rclone's configuration; its `obscure` command cannot be used for this field. The resulting configuration file is owner-readable only (`0600`) but contains this scoped key in plaintext. Protect the Mac login with a strong password and enable FileVault. Never share the rclone config file. If the helper cannot connect, it leaves the prior configuration unchanged and uploads no shop data. Backblaze [documents the two-value mapping](https://www.backblaze.com/apidocs/b2-authorize-account); a 401 on the authorization request means the key pair was rejected, while a later bucket-listing error can mean missing permission.

Alternatively, run `rclone config` in Terminal and answer its prompts:

1. `n` for a new remote, then name it `invora-b2`.
2. Choose `b2` for storage (Backblaze B2, not S3).
3. At `account>`, enter the Backblaze **keyID**. At `key>`, enter the **applicationKey**.
4. Leave `endpoint>` blank, accept the remaining defaults, confirm that the remote is saved, and quit with `q`.

Set `BACKUP_RCLONE_REMOTE=invora-b2:your-bucket-name/shop-01` when running the backup command. The remote name is local to this Mac; it does not change the Backblaze bucket.

The current recipient private key and matching shop `.env` are on this Mac. An offsite archive is useless after total disk loss unless the recovery key and private configuration also survive **separately**. Copy them to protected offline storage or a trusted password manager under the owner's control; do not upload plaintext copies to the backup bucket. Confirm that the recovery copy can be opened before relying on the cloud archive.

After configuration, download a recent archive and its `.sha256` file to an isolated machine, verify the checksum, run `scripts/restore.sh` against a new `invora_restore_...` database, and run `scripts/reconcile.sql`. Check an invoice, stock quantities, customer dues and uploaded documents before declaring recovery ready. Repeat this rehearsal at least monthly and after a major update. The [storage and security guide](data-storage-security.md) describes the device-move sequence.

## This Mac's daily Backblaze push

On 23 October 2026, this Mac's owner configured private bucket `invora` as rclone remote `invora-b2` and installed `~/Library/LaunchAgents/com.invora.backup.plist`. The agent invokes `scripts/run-scheduled-backup.sh` **daily at 9:00 PM local Mac time**. Its owner-only configuration is `.private-backups/backup-schedule.env`; the rclone credential is in `~/.config/rclone/rclone.conf`, also owner-only. It uses `scripts/backup-offsite.sh`, so API/web pause briefly for a consistent dump and then restart before upload. It uploads a new uniquely named archive and checksum; it never synchronizes or deletes older remote copies. Failed runs leave `.private-backups/backblaze-invora/last-failure-utc`, append `scheduled-backup.log`, and request a macOS notification. A notification can be missed or blocked, so **check `last-success-utc` every morning**. The job requires this Mac to be logged in/awake or woken, Docker Desktop running, a network connection and the rclone credential still valid.

The schedule was triggered once via `launchctl kickstart gui/$(id -u)/com.invora.backup` and exited 0. The pre-clean archive `invora-20261023T090207Z-RzOLRK.backup` and post-clean archive `invora-20261023T090947Z-94RtON.backup` were uploaded, downloaded and compared byte for byte against their SHA-256 sidecars. Both signed archives restored into isolated PostgreSQL databases and passed financial reconciliation; the clean one also retained owner/catalog records while its operational tables were empty. The earlier archive intentionally contains records removed from the live shop and remains a private recovery generation. This is a live-data cleanup, **not secure erasure** of historical backups or audit entries.

To check the job, run `launchctl print gui/$(id -u)/com.invora.backup` and read `.private-backups/backblaze-invora/last-success-utc`. To retry a failed push, run `bash scripts/run-scheduled-backup.sh` from the installation folder while Docker Desktop is running. The `last-success-utc` marker and log are on this Mac and can disappear with the disk; also check the bucket's dated archive list periodically. There is no second-drive copy yet and no independent remote alert if this Mac never runs the job.

**Recovery key still needs an off-computer copy.** The recipient private key, matching `.env`, and trusted signing public key remain on this Mac. An archive in Backblaze cannot restore the shop after complete Mac loss without the private key. Store those files together in protected offline storage or an owner-controlled password manager, separate from the B2 bucket credential, and test that they can be retrieved. The B2 key is scoped to the bucket but the local rclone config contains it in plaintext, protected by owner-only file mode and the Mac's disk/login security. Periodic restore rehearsals and a suitable bucket retention policy remain the owner's operational responsibilities.
